# COLOR_SPEC — 색 공간과 상대값 규칙

core/color의 계산 규칙. 여기서 정한 상수·공식이 바뀌면 모든 Lab 값과 골든 스냅샷이 바뀐다.
따라서 이 문서의 상수는 튜닝 대상이 아니라 **고정 규약**이다. 변경은 사용자 승인 + baseline 재확정이 필요하다.
`[미결]`은 PLAN.md 미결 사항과 대응한다.

## 1. 색 공간

### 1.1 입력: sRGB
- 입력은 sRGB(IEC 61966-2-1), 8비트 `0~255` 또는 `#RRGGBB`. 알파 없음.
- sRGB는 **입출력 표현**으로만 쓴다. 비교·거리·판정에 쓰지 않는다 (§4).

### 1.2 변환 사슬
```
sRGB(8bit) → sRGB(0~1) → 선형 RGB → XYZ(D65) → CIELAB(D65) → LCh
```
역변환은 같은 사슬을 거꾸로 간다. 팔레트 hex 검증(hex→Lab)과 표시용 hex 생성(Lab→hex)에 쓴다.

**감마 (sRGB 전달 함수)**
```
c ≤ 0.04045 :  c_lin = c / 12.92
c >  0.04045 :  c_lin = ((c + 0.055) / 1.055) ^ 2.4
역:  c_lin ≤ 0.0031308 : c = 12.92 · c_lin
     그 외              : c = 1.055 · c_lin ^ (1/2.4) − 0.055
```

**선형 RGB → XYZ (D65)** — Bruce Lindbloom sRGB 행렬
```
X = 0.4124564·R + 0.3575761·G + 0.1804375·B
Y = 0.2126729·R + 0.7151522·G + 0.0721750·B
Z = 0.0193339·R + 0.1191920·G + 0.9503041·B
```
**XYZ → 선형 RGB**
```
R =  3.2404542·X − 1.5371385·Y − 0.4985314·Z
G = −0.9692660·X + 1.8760108·Y + 0.0415560·Z
B =  0.0556434·X − 0.2040259·Y + 1.0572252·Z
```
역변환 결과가 `[0,1]`을 벗어나면(sRGB 색역 밖) `[0,1]`로 클램프하고 diagnostics에 `WARN`을 남긴다. 조용히 자르지 않는다.

**XYZ → Lab (기준 백색 D65, 2° 관측자)**
```
Xn = 0.95047,  Yn = 1.00000,  Zn = 1.08883
f(t) = t^(1/3)                 (t > ε)
     = (κ·t + 16) / 116        (t ≤ ε)
ε = 216/24389,  κ = 24389/27
L = 116·f(Y/Yn) − 16
a = 500·(f(X/Xn) − f(Y/Yn))
b = 200·(f(Y/Yn) − f(Z/Zn))
```

**Lab → LCh**
```
C = √(a² + b²)
h = atan2(b, a) 를 도(°)로 변환해 [0, 360) 로 정규화
```
h 기준: `0°` = +a(레드~마젠타), `90°` = +b(옐로우), `180°` = −a(그린), `270°` = −b(블루). 시계 반대 방향으로 증가.

### 1.3 값 범위와 타입
- `L ∈ [0,100]`, `a, b ∈ [-128,127]`, `C ≥ 0`, `h ∈ [0,360)`. 모두 `Double`.
- 중간 계산에서 반올림하지 않는다. 반올림은 JSON 출력 시 한 번만, 고정 자릿수로 한다 ([미결]: 소수 3자리 제안).
- 상수는 위에 적힌 출처로 고정한다. 다른 출처의 근사값(예: Xn=0.9505)을 섞지 않는다.

### 1.4 무채색과 뉴트럴
- `C`가 무채색 임계 미만이면 hue는 정의되지 않는다. 이때 hue 비교(ΔHue, 조화 구간)를 하지 않고 diagnostics에 `INFO`로 남긴다.
- 무채색 임계는 규칙 JSON 파라미터다 (코드 상수 금지). 확정값 **C* < 5**, `harmony_rules_v1.json`에 둔다.
  근거: C*=5에서 a/b 1단위 오차가 hue를 약 11° 흔들고, C*=2에서는 약 28° 흔든다. 그 아래는 hue 판정에 쓸 수 없다.
- 중성형 전략의 재료(팔레트의 뉴트럴)는 채도 임계가 아니라 팔레트의 **`neutral` 태그**로 정한다 (RULES_SCHEMA §2.2).
  채도만으로는 정의할 수 없기 때문이다: camel(C* 31)·navy(C* 18)은 뉴트럴이지만 sage(C* 15)·blush(C* 14)는 아니다.
- "저채도" 판정 임계는 얼굴 제약(피부 색상대 고채도 회피, 저채도 허용)에서만 쓰이므로 `face_constraints_v1.json`에서 정한다. 값은 [미결].

## 2. 상대값 (RelativeFeature)

Stage 4의 출력이자 Stage 5의 입력. 피부(`skin`)를 기준으로 립(`lip`)의 상대 위치를 나타낸다.
촬영 조명이 바뀌면 절대 Lab은 함께 움직이지만 피부–립의 차이는 비교적 유지된다는 가정 위에 있다 (3단계 조명 실험에서 검증).

| 값 | 정의 | 범위 | 비고 |
|---|---|---|---|
| `ΔHue` | 립 hue − 피부 hue의 **부호 있는 원형 차** | `[-180, 180)` | 한쪽이 무채색이면 `null` |
| `ΔL` | `L_lip − L_skin` | `[-100, 100]` | 보통 음수 (립이 피부보다 어둡다) |
| `ΔC` | `C_lip − C_skin` | | 보통 양수 (립이 더 선명하다) |

**원형 차 계산**
```
d = ((h_lip − h_skin + 540) mod 360) − 180      // [-180, 180)
|ΔHue| = |d|                                     // [0, 180]
```
부호: 양수 = 립이 피부보다 시계 반대 방향(hue 증가 방향, 예: 레드 피부 기준 옐로우 쪽).
조화 구간 판정은 **|ΔHue|**를 쓴다. 부호는 진단·표시용이다.
매치형 전략의 "±25~45" 양쪽 후보를 부호로 구분해 다룰지는 RULES_SCHEMA에서 확정한다 ([미결]).

**조화 구간값의 근거에 대한 주의.** 조화 구간(0~5 동일, 5~25 제1부조화, 25~45 유사, 45~100 제2부조화, 100~180 대비)은
Moon-Spencer 조화론을 착안점으로 한 **CIELCh 각도의 초기 추정치**다. 원 이론은 먼셀 색상환 기준이고,
먼셀과 CIELCh는 색상 간격이 다르므로 먼셀에서 90° 떨어진 두 색이 CIELCh에서 90°가 아니다.
따라서 이 구간값은 원 이론의 수치와 일치하지 않으며 "이론대로 넣었는데 왜 다르지"는 정상이다.
구간값의 확정은 2단계 검수에서 한다. RULES_SCHEMA.md의 해당 파라미터 설명에도 같은 취지를 적는다.

**의상 후보에 대한 상대값** (Stage 5에서 계산, 같은 정의)
- 의상–립: `|ΔHue|(garment, lip)` → 조화 구간, `C_garment − C_lip` → 채도 제약
- 의상–피부: `|L_garment − L_skin|` → 명도차 하한, `h_garment`가 피부 색상대 회피 범위에 드는지 + `C_garment` 조건

## 3. 색차 (ΔE)

| 공식 | 정의 | 사용처 (제안, [미결]) |
|---|---|---|
| `ΔE*ab` (CIE76) | `√(ΔL² + Δa² + Δb²)` | 로더의 hex↔Lab 일치 검증 (단순, 허용 오차만 필요) |
| `ΔE00` (CIEDE2000) | CIE 2000 공식, `kL = kC = kH = 1` | 지각 비교 전부: 피부–립 구분 판정, 팔레트 근접 판단 |

CIEDE2000은 구현 오류가 흔하다. Sharma, Wu, Dalal (2005)의 테스트 데이터 쌍으로 유닛 테스트한다.

## 4. RGB 공간에서 거리 계산을 금지하는 이유

1. **비선형이다.** sRGB 값은 감마가 걸려 있어 `(10,10,10)`과 `(20,20,20)`의 차이는 `(200,200,200)`과 `(210,210,210)`의 차이와 지각상 전혀 다르다.
2. **지각 비균등이다.** 같은 유클리드 거리가 그린 영역에서는 거의 안 보이고 블루 영역에서는 크게 보인다. "명도차 15 이상" 같은 규칙을 RGB에서는 정의할 수 없다.
3. **명도·채도·색상이 얽혀 있다.** RGB 세 축은 지각 속성과 대응하지 않아 "채도만 낮춘다", "색상만 30° 돌린다"를 표현할 수 없다. HSV/HSL도 장치 종속적이고 V/S가 지각 명도·채도와 다르므로 같은 이유로 금지한다.
4. **조명 변화가 세 채널에 불균등하게 실린다.** Lab에서는 조명 변화가 주로 L과 완만한 a/b 이동으로 나타나 상대값이 살아남는다. RGB 차이는 조명에 따라 크게 흔들린다.

허용되는 RGB 사용: 입력 파싱, 표시용 hex 생성, 팔레트 hex↔Lab 일치 검증. 셋 모두 §1.2 변환을 거친다.

## 5. 수치 안정성과 결정론

- 계산은 `kotlin.math`(`pow`, `cbrt`, `sqrt`, `atan2`, `cos`, `sin`)만 쓴다. `java.lang.Math`/`StrictMath` 직접 호출 금지 (CONTRACT §6).
- `pow(x, 1/3)` 대신 `cbrt`를 쓴다 (음수 입력 안전, 정밀도).
- 구간 경계는 반개구간 `[min, max)`로 통일하고, 경계값 테스트를 둔다.
- 플랫폼(JVM 버전, CPU)에 따라 초월함수 마지막 비트가 다를 수 있다. 출력 반올림 자릿수 고정과 id 기준 동점 처리로 스냅샷을 안정시킨다. 경계에 정확히 걸리는 값이 뒤집히면 골든 diff에서 드러난다.
- 소수 자릿수 고정은 `String.format`이 아니라 산술 반올림(`round(x · 10^n) / 10^n`)으로 한다 (로케일 비의존).

## 6. 뷰어에 대한 규칙

뷰어(prototype/)는 색 계산을 하지 않는다. 필요한 hex, Lab, LCh, Δ값은 모두 Kotlin이 결과 JSON에 담아 보낸다.
같은 공식을 JS로 다시 쓰는 것은 금지다 (엔진은 하나).
유일한 예외: 팔레트 스와치(`prototype/palette.html`)가 저장된 Lab에서 C* = √(a²+b²), h° = atan2(b, a)를 표시용으로 계산하는 것.
이는 저장값의 극좌표 표기이며 결과에 영향을 주지 않는다. sRGB↔Lab 등 색 공간 변환과 배색 로직은 여전히 금지다.
